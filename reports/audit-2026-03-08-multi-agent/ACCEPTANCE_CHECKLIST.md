# QA/UX Acceptance Checklist (Wave 1)

**Дата:** 2026-03-08  
**Релиз:** Wave 1  
**Цель:** подтвердить готовность ключевого пользовательского пути к релизу: `landing -> auth -> first deploy -> domain/ssl -> upgrade`.

---

## 1) User Journey Acceptance (E2E)

### A. Landing
- [ ] Главный CTA виден без скролла на desktop (≥1280px)
- [ ] На mobile (375px) CTA и основной value proposition читаемы без UI-ломаний
- [ ] Кнопки `Sign up / Start free / Deploy now` ведут на корректный auth-flow
- [ ] Время загрузки первого экрана (LCP) в норме (целевой ориентир: < 2.5s на нормальной сети)
- [ ] Нет критических визуальных дефектов (наложения, сдвиги, обрезанный текст)

**UX-критерии:**
- [ ] Пользователь за ≤5 секунд понимает: что это за продукт, для кого, и что делать дальше
- [ ] На первом экране только 1 главный CTA (или явный приоритет CTA)

---

### B. Auth (регистрация / вход)
- [ ] Регистрация с валидными данными проходит успешно
- [ ] Ошибки валидации полей понятны и локализованы (email, пароль, обязательные поля)
- [ ] Повторная попытка после ошибки проходит без «залипания» формы
- [ ] Вход существующего пользователя работает
- [ ] После login/signup редирект ведёт в правильный onboarding/console state
- [ ] Сессия сохраняется после refresh
- [ ] Logout завершает сессию и защищённые страницы больше недоступны без входа

**UX-критерии:**
- [ ] Тексты ошибок объясняют «что не так» и «что делать»
- [ ] Время ответа auth API не вызывает ощущения «зависло» (есть loader/feedback)

---

### C. First Deploy (первый деплой)
- [ ] Пользователь может создать первый проект без обращения к документации
- [ ] Минимальный happy path: `Create app -> Configure basic settings -> Deploy` работает end-to-end
- [ ] Статусы деплоя отображаются последовательно (queued/building/deployed/failed)
- [ ] Для failed состояния есть понятная диагностика и следующий шаг
- [ ] После успешного деплоя есть рабочая ссылка/preview
- [ ] Повторный деплой (redeploy) работает

**UX-критерии:**
- [ ] Прогресс деплоя прозрачен (пользователь видит, что происходит)
- [ ] Нет «молчаливых» падений без сообщения

---

### D. Domain + SSL
- [ ] Кастомный домен добавляется в проект
- [ ] Инструкции по DNS корректны и понятны (A/CNAME, где проверить)
- [ ] Статус проверки домена обновляется корректно (pending/verified/error)
- [ ] SSL выпускается автоматически после корректной DNS-конфигурации
- [ ] HTTPS доступен, редирект с HTTP на HTTPS работает
- [ ] Для ошибок (неверный DNS, таймаут) есть понятные сообщения и шаги исправления

**UX-критерии:**
- [ ] Пользователь понимает текущий шаг подключения домена
- [ ] Нет скрытых требований (всё критичное явно написано в интерфейсе)

---

### E. Upgrade (переход на платный план)
- [ ] Ограничение free-плана корректно триггерит upgrade-поток
- [ ] Экран тарифов прозрачно объясняет различия планов
- [ ] Путь `Select plan -> Checkout -> Confirmation` завершает апгрейд
- [ ] После оплаты права/лимиты обновляются без ручного вмешательства
- [ ] При неуспешной оплате отображается понятный recovery-flow
- [ ] История/статус подписки отражаются в аккаунте

**UX-критерии:**
- [ ] Нет неоднозначности в цене, периоде, автопродлении
- [ ] Подтверждение успешного апгрейда явно видно (toast/screen/email)

---

## 2) Definition of Done (DoD) — Wave 1

Wave 1 считается готовой к релизу, если выполнены все пункты ниже:

### Product / UX
- [ ] Основной E2E journey (5 этапов выше) проходит без блокеров (Severity S1/S2 = 0)
- [ ] Критичные UX-фрикции из smoke-прохода закрыты или имеют согласованный mitigation
- [ ] Копирайтинг ошибок и состояний пустого экрана понятен и консистентен

### QA / Reliability
- [ ] Все P0/P1 тест-кейсы пройдены
- [ ] Нет открытых критических дефектов: security/data-loss/payment/deploy-blocker
- [ ] Нестабильные баги задокументированы с воспроизводимостью и owner
- [ ] Выполнен регресc по затронутым модулям

### Technical / Performance
- [ ] Нет блокирующих ошибок в production-логах на ключевых сценариях
- [ ] Core pages не имеют критической деградации производительности
- [ ] Обработка ошибок API единообразная в UI

### Billing / Domain Risk
- [ ] Upgrade-поток проверен на success/fail сценариях
- [ ] Domain+SSL поток проверен на happy path + типовые ошибки DNS

### Release Governance
- [ ] Есть release notes для Wave 1
- [ ] Назначен owner пост-релизного мониторинга (первые 24-48ч)
- [ ] Go/No-Go решение зафиксировано (дата, ответственный)

## 3) Manual Pre-Release Test Suite

Ниже — обязательный ручной прогон перед релизом.

## 3.1 Smoke (15–25 мин)
1. [ ] Открыть landing на desktop/mobile, проверить CTA
2. [ ] Пройти signup/login
3. [ ] Создать проект и запустить первый деплой
4. [ ] Открыть деплойнутый URL
5. [ ] Добавить тестовый домен (или staging-домен), проверить статус верификации
6. [ ] Проверить upgrade-flow до финального шага подтверждения

**Критерий pass:** весь путь проходится без блокеров.

## 3.2 Functional Deep Checks

### Auth
- [ ] Невалидный email -> понятная ошибка
- [ ] Слабый пароль -> понятная ошибка + требования
- [ ] Уже существующий email -> корректное сообщение
- [ ] Logout/login cycle без потери целостности аккаунта

### Deploy
- [ ] Deploy с валидной конфигурацией -> success
- [ ] Deploy с намеренно плохой конфигурацией -> корректная ошибка
- [ ] Повторный deploy после фикса -> success

### Domain/SSL
- [ ] Неверная DNS запись -> отображается actionable error
- [ ] После исправления DNS статус обновляется до verified
- [ ] Сертификат активен, HTTPS без предупреждений браузера

### Upgrade/Billing
- [ ] Успешная оплата -> план обновлён
- [ ] Неуспешная оплата -> нет ложного апгрейда
- [ ] Повторная попытка оплаты доступна и корректна

## 3.3 UX/Content Checks
- [ ] Тексты кнопок и статусов однозначны
- [ ] Пустые/ошибочные состояния не оставляют пользователя «в тупике»
- [ ] Для ключевых действий есть видимая обратная связь (loader/toast/status)
- [ ] Нет смешения языков в одном critical flow (если это не часть требований)

## 3.4 Cross-Environment Matrix
- [ ] Chrome (latest)
- [ ] Safari (latest)
- [ ] Mobile viewport (iOS Safari / Android Chrome)
- [ ] Staging конфигурация соответствует production-ожиданиям

---

## 4) Defect Severity Gate

- **S1 (Blocker):** пользователь не может завершить ключевой этап journey  
- **S2 (Critical):** этап формально завершён, но результат некорректен/опасен (например, неверный billing state)  
- **S3 (Major):** есть workaround, но заметная деградация UX/надежности  
- **S4 (Minor):** косметика, не мешает выполнению сценария

**Release rule:**
- [ ] S1 = 0
- [ ] S2 = 0
- [ ] S3: только с подтверждённым owner + сроком фикса
